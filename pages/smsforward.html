SMSForward（SmsForwarder）对接教程

没有短信供应商回调？用一台安卓备用机 + 开源应用 SmsForwarder，把验证码短信实时转发到 SMSServer 的 webhook。

本教程的通用模式（/api/v1/webhook/sms/{token}）在当前代码即可用；通道模式（/api/v1/webhook/smsforward/...）依赖尚未合入本分支的上游 PR #1，合入前请用通用模式。

工作原理

验证码短信到达备用机
      │  SmsForwarder 按转发规则触发
      ▼
webhook 请求（消息模板占位符替换后的 JSON）
      │  POST {服务地址}/api/v1/webhook/sms/{WEBHOOK_SECRET}
      ▼
SMSServer 提取验证码，按收件人号码（= 备用机 SIM 卡号）落缓存
      │
      ▼
你的业务系统用 HMAC(备用机号码) 轮询 /api/v1/otp 取码，取走即焚

关键点：SMSServer 侧的「收件人号码」就是备用机插的那张 SIM 卡的号码。SmsForwarder 的占位符里没有「本机号码」，所以 recipient 要在模板里写死。

配置生成器

填写下方参数，直接生成可粘贴进 SmsForwarder 的 webhook 地址与消息模板：

webhook 地址 —— 填入 SmsForwarder「Webhook 通知」的 Server 栏
# 填写上方配置后生成
消息模板（webParams）—— 填入「消息模板」栏，JSON 格式
# 填写上方配置后生成

SmsForwarder 侧配置步骤

  1. 安装应用：从 GitHub Releases 或 Gitee 镜像下载，安装到插着目标 SIM 卡的备用机，授予短信、通知等权限。
  2. 开启短信转发：首页开启「转发短信」；在「转发规则」里添加规则，匹配方式可选「全部」或按关键词（如包含 验证码）。
  3. 添加 Webhook 发送通道：「发送通道」→ 新建 → 选「Webhook」，按下表填写：
    SmsForwarder 界面项填写值
    请求方式POST
    Server（服务器）上方生成器输出的 webhook 地址
    消息模板（webParams）上方生成器输出的 JSON 模板
    请求头无需手动添加（App 发 JSON 请求体时自动带 Content-Type: application/json）
    签名（secret）留空（SMSServer 不校验 SmsForwarder 的 sign 字段）
  4. 测试：用另一台手机给备用机发一条验证码短信，或直接在规则页用「测试」按钮发送。SmsForwarder 会显示服务端响应，预期 {"status":"ok"}。
  5. 验证取码：用首页取码助手生成取码命令（号码填备用机 SIM 卡号），在部署机上执行，预期返回 {"status":"success","code":"..."}。

消息模板占位符对照

下表来自 SmsForwarder 源码（Constants.kt 的 TAG_LIST），中文占位符与英文占位符等价，模板里用哪个都行：

占位符含义填入 SMSServer 的字段必填
{{FROM}} / {{来源号码}}短信发送方号码sender否
{{SMS}} / {{短信内容}}短信全文body（提取验证码的来源）是
无占位符，手工填死备用机 SIM 卡号recipient（HMAC 的计算依据）是
{{DEVICE_NAME}} / {{设备名称}}设备备注名source（通道模式的白名单依据）通道模式建议带上
{{CARD_SLOT}} / {{卡槽信息}}卡槽标识可拼进 provider 区分双卡否
{{RECEIVE_TIME}} / {{接收时间}}短信接收时间无需填入（服务端自行记录接收时间）否
SmsForwarder 对 JSON 请求体（{ 开头的模板）会自动做 JSON 转义后发送，短信内容里的引号、换行不会破坏报文，无需手工处理。

通道模式：多设备独立鉴权（需 PR #1）

通用模式下所有转发设备共享同一个 WEBHOOK_SECRET。上游 PR #1 引入多通道后，每台备用机可以有自己的密钥，并可绑定提取模板与来源白名单：

POST /api/v1/webhook/smsforward/{channel_id}/{token}

服务端用环境变量 SMSFORWARD_CHANNELS_JSON 声明通道（自托管版；Workers 版对应 secret/vars）：

[
  {
    "channel_id": "android-main",
    "webhook_secret": "<openssl rand -hex 32>",
    "enabled": true,
    "provider": "smsforward",
    "source_whitelist": ["备用机1"]
  }
]
  • webhook_secret 是该通道独立的路径密钥，泄漏后只需吊销这一个通道
  • 配置了 source_whitelist 时，请求体 source 必须命中（对应模板里的 {{DEVICE_NAME}}），否则拒绝
  • 配合 OTP_TEMPLATES_JSON 可为该通道指定关键词/字母数字混合的提取模板，比通用数字正则更准，详见仓库 docs/WIKI_SMSFORWARD_TEMPLATES.md

常见问题

SmsForwarder 显示 401 unauthorized

webhook 地址里的密钥与服务端不一致：检查是否复制完整（openssl rand -hex 32 生成的 64 位十六进制）、URL 是否含多余层级。通用模式路径必须是 .../sms/{WEBHOOK_SECRET}；通道模式是 .../smsforward/{channel_id}/{token}，两者不能混用。

webhook 返回 ok 但取码一直 pending

最常见原因是 recipient 与取码时的号码不一致：模板里写死的 SIM 号码（如 13900000000）与取码命令里的号码（如 +8613900000000）必须逐字符相同，HMAC 才会对得上。其次是验证码已过期或已被取走（阅后即焚）。

取到的码是订单号/金额？

通用提取是「第一个 4-8 位数字」的启发式。改用更精确的匹配：转发规则里只放行含「验证码」关键词的短信；或等 PR #1 合入后为通道配置模板提取。

双卡手机两个号码怎么区分？

每张卡建一个转发规则，模板里 recipient 分别写死两张卡的号码；通道模式下则建两个通道。取码时用对应号码的 HMAC 分别查询。

安全注意事项

  • 备用机只插专用 SIM 卡，不装其他业务应用；开启锁屏与远程查找
  • webhook_secret 等同「向该号码注入验证码」的权限，泄漏立即更换（通道模式只需换对应通道）
  • 生产环境建议给 /api/v1/otp 前面加网关层限流，防止 token 被暴力遍历
  • SmsForwarder 本身不上传隐私数据（开源可审计），但转发目标地址即本服务，请确认部署环境可信
