token 计算

输入收件人号码与 HMAC_SECRET，在浏览器本地算出取码 token。本页同时解释「哪些值要计算、哪些值静态设置」，并给出与日志对账的排查法。

本计算器用于自托管 / Docker。Cloudflare Workers 版只有一个 TOKEN，无需本页：取码直接发 {"token":"TOKEN"} 即可。

计算工具

token 是确定性计算：同样的两个输入永远得到同样的结果，所以不存在「token 过期」或「服务端发放」——算错了重算即可，不用联系服务端。

取码 token = hex(HMAC-SHA256(key=HMAC_SECRET, msg=收件人号码))

要计算，还是静态设置？

文档里会看到「recipient 要在模板里写死」和「调用方算出 token」两种说法，容易混。它们其实指的是三个不同的东西：

值本质谁在哪设置改的时候怎么办
WEBHOOK_SECRET 静态密钥 你，部署时一次性配置；短信来源方把它拼在 webhook URL 里 轮换后来源方必须同步改 URL，旧 URL 立即 401
HMAC_SECRET 静态密钥 你，部署时一次性配置；取码方本地持有 轮换后所有在途验证码对取码方立即不可见，取码方必须用新密钥重算
recipient 请求体里的固定字段 来源方写进转发模板（SmsForwarder 没有「本机号码」占位符，只能手工填 SIM 卡号）；取码方查询时用同一字符串 换 SIM 卡号时，模板与取码命令两处必须同步改
取码 token 派生值，不是配置 取码方在发起查询时用 recipient + HMAC_SECRET 现算（本页或首页取码助手） 输入不变则结果永不变，无需任何「设置」动作
服务端没有「设置取码 token」这回事。服务端不保存任何 token 表：收到 webhook 时用请求体里的 recipient 现算存储 key，收到查询时用你算的 token 查表。两边不是「一个设置、一个读取」，而是用同一个公式各自现算、结果自然对上。这也是取码接口不需要任何密钥头的原因——token 本身就是凭据。

对不上时怎么排查

  1. 先比前 8 位：让短信真正到达一次（webhook 返回 {"status":"ok"} 且 body 里有 4-8 位数字），在 Workers 日志或 wrangler tail 里找 [短信] 处理完成 recipient_hash=xxxxxxxx，与上方工具算出的 token 前 8 位比对。不一致 = 密钥或号码字符串有一处不同（空格、有无 +86、用了 sender 而非 recipient 算的都会导致）。
  2. 本地交叉验证密钥：复制上方「python3 对照验证」命令在你自己机器上跑一遍，与工具输出不一致说明两处 HMAC_SECRET 抄录不同。
  3. webhook 返回 400 invalid json：多半是 Windows cmd 把单引号原样发出去了（cmd 不认单引号定界符）。body 存成 UTF-8 文件后用 curl -d @body.json，或改用双引号转义写法。
  4. 取码一直 pending：按顺序排除——token 没对上（回到第 1 步）；码已被之前的查询取走（阅后即焚，重发一条短信再试）；短信 body 里根本没有 4-8 位数字（webhook 会照样返回 ok 但不落库）；超过有效期（OTP_TTL_SECONDS）。

需要看字段级说明与完整响应表，见 接口文档 · token 计算方式；安卓备用机转发场景见 SMSForward 对接教程。
